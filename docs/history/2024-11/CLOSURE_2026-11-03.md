## 一、根因与修复

### 1. P0：PPT 域装配链（行模型 vs 服务解耦）

**现象**：`dsh-suite.json` 的 `rows` 没有 `ppt-workbench-host`，`dsh-suite compose` 只按 rows
生成 patch（13 行），而 `dsh-domain.json` 仍用 `runtime.bindings`/`removeRows` 引用它；
`dsh-ppt-workbench/lib/host.mjs` 已标记退役（服务解耦）。结果：content 端口无人监听，
`verify-chain` 8/10、`suite-kit` 66/68、`workspace-service` PPT E2E 30s 超时。

**修复（不是把退役行加回去）**：让 domain runtime 走服务解耦标准。

- `packages/dsh-suite-kit/src/runtime.mjs`
  - 新增 `collectSuiteServices`：读 suite 根 `services.json`（broker spec 形状）。
  - 新增 `materializeServiceManifest`：物化 `<runtime>/service-manifest.json`
    - `portFrom: "content"` → 主端口 = runtime content 端口（PPT relay / MCP / 检查同端口）
    - `dirFrom: "contentState"` → `--dir` 指向 runtime 内容目录
    - `${PACKAGE_DIR}/node_modules/<pkg>` → 包实际目录；其余 `${PACKAGE_DIR}` → suite 目录
  - `createRuntime`：收集服务、分配 broker/服务端口（进 runtime 端口租约）、写物化清单。
  - `startRuntime`：拉起 `dsh-service-broker`（独立进程，`--stop-on-exit`），等 broker `/healthz`；
    `DSH_DISCOVERY_FILE` 指向 runtime 私有 discovery；harness 就绪改为 HTTP 根路径可响应
    （避免 proxy 已监听、dsh 还在加载时的假就绪）。
  - `stopRuntime`/`removeRuntime`：先停 broker（防 keepAlive），再按 discovery PID 补杀 detached 服务。
  - `doctorRuntime`：增加 broker 健康检查；`runtimePublicInfo` 暴露 `services`。
- `extensions/bridges/ppt-bridge/domains/ppt/dsh-domain.json`
  - 删除 `ppt-workbench-host` 的 `runtime.bindings` 与 `removeRows`。
  - 增加 `runtime.ports.services.dsh-skills = 39321`。
- `extensions/bridges/ppt-bridge/plugin/dsh-ppt-suite/services.json`
  - `ppt-workbench` 增加 `portFrom: "content"`、`dirFrom: "contentState"`。
- `extensions/bridges/ppt-bridge/plugin/dsh-ppt-workbench/server/relay.mjs`
  - standalone 入口从 `DSH_RUNTIME_FILE`/`DSH_STORE_*` 接上当前 runtime 的 workspace store，
    不再退化成全局 `~/.dsh-ppt-bridge` 文件库；hostDir 缺省取 runtime contentState。
- `packages/dsh-workspace-service/test/e2e.test.mjs`
  - PPT fixture 去掉退役行 binding；health 断言改为服务解耦形态
    （`serviceHost/toolHost/editorHost=false`、`assets=true`）。

## 三、仍然保留的边界（诚实声明）

1. **两条装配入口已在清单层统一、底层路径仍不同**：`dsh-stack.json` v2 用 `kind=profile|domain`
   共用 `dshd` 入口；profile 走编译，domain 走 runtime（有意保留差异）。`.works` 的
   autoStart/钩子仍归 `dsh-deploy` 部署配置。详见 `STACK_V2_2026-11-03.md`。
2. **PPT suite/workbench/8 skills 仍未进发布源**：它们缺少 `engines.dsh`，且 suite 的
   `packages[].path` 是源码树相对路径，直接打 zip 需要在打包侧重写；当前作为内部装配工件
   使用，不作为可分发插件。
3. **`plugin-development/my-plugins/dsh-flow-engine` 反向闭环测试仍红**：它仍写旧
   `registry.json`，与 `works-registry.json` 分治未对齐（CHAIN_CONTRACTS 待办 4）。
   已从正式 `test-all` 门禁排除，未改动该实验插件。
4. **没有远端 publish/CI**：`release-all`/`release-source` 产源到本地；推到静态 HTTP/对象存储
   仍需外部步骤（或后续加 `release --publish`）。
5. **bridges 可选验证仍不达标**：`canvas-bridge`、`ppt-bridge` 的独立架构不符合官方插件规范；
   `validate-all` 明确标注为可选。

## 四、下一步建议

1. stack-kit v2：把 domain/services 纳入 `dsh-stack.json`，让 `dshd --stack` 与 domain runtime

3. 对齐 `dsh-flow-engine` 的 works 注册写入口，纳入正式门禁。
4. 加 publish 命令或 CI：`validate-all` + `verify-chain` + `test-stack:all` + `release-all` 一条流水线。
