## 🔑 核心区别

### Cordis（运行时）

```javascript
// Cordis 回答：HOW（如何运行）

export function apply(ctx, config) {
  // 插件如何加载
  ctx.myService = new MyService()
  
  // 依赖如何注入
  const otherService = ctx.otherService
  
  // 资源如何清理
  ctx.on('dispose', () => { ... })
}
```

**职责**：
- ✅ 加载插件代码
- ✅ 管理依赖关系
- ✅ 提供上下文
- ✅ 处理生命周期

### 你的启动清单系统（编译时）

```javascript
// 启动清单回答：WHAT（运行什么）

{
  "name": "dev",
  "profile": "web",
  "plugins": {
    "bundles": ["dsh-base", "my-plugin"]
  },
  "services": [
    { "id": "my-service", "port": 39311 }
  ]
}
```

**职责**：
- ✅ 选择哪些插件
- ✅ 配置环境参数
- ✅ 编排服务启动
- ✅ 管理多环境

## ✅ 为什么不是重复？

### 原因 1: 不同的抽象层次

```
高层（What）  →  启动清单系统
                ↓
中层（How）   →  Cordis
                ↓
底层（硬件）  →  Node.js/OS
```

### 原因 2: 解决不同的问题

| 问题 | Cordis | 启动清单 |
|------|--------|----------|
| 如何加载插件？ | ✅ | ❌ |
| 运行哪些插件？ | ❌ | ✅ |
| 如何注入依赖？ | ✅ | ❌ |
| 配置多环境？ | ❌ | ✅ |
| 如何热重载？ | ✅ | ❌ |
| 如何可视化管理？ | ❌ | ✅ |

### 原因 3: 相互依赖

```javascript
// 启动清单生成 Cordis 配置
launchpad.compile('dev.stack')
  → generates cordis.patch.yml

// Cordis 加载启动清单生成的配置
cordis.load('cordis.patch.yml')
  → loads plugins defined in stack
```

**它们是合作伙伴，不是竞争对手！**

## 🎯 最佳实践

### DO（应该做的）✅

1. **保持分层架构**
   ```
   Launchpad → Stack Kit → Suite Kit → Cordis
   ```

2. **以 stack.json 为真源**
   ```json
   // 唯一手写的配置
   {
     "name": "dev",
     "plugins": [...],
     "services": [...]
   }
   ```

3. **生成物标记为 DO NOT EDIT**
   ```yaml
   # cordis.patch.yml
   # ⚠️ DO NOT EDIT - Generated from dsh-stack.json
   - insert: ...
   ```

4. **利用 Cordis 的优势**
   ```javascript
   // 在插件中使用 Cordis 的能力
   export function apply(ctx, config) {
     ctx.on('ready', ...) // 生命周期
     ctx.emit('event')    // 事件
   }
   ```

### DON'T（不应该做的）❌

1. ❌ 手写 cordis.patch.yml（应该由 Stack Kit 生成）
2. ❌ 绕过 Launchpad 直接修改 profile（保持一致性）
3. ❌ 混淆编译时和运行时的职责
4. ❌ 试图用 Cordis 替代启动清单系统
